# Flight link control contract v1 — LRC2/LRA2

状态：E1/E2/H 协作接口草案，2026-11-14。仅地面联调 `echo` 和 `status`；不接飞控、不执行飞行动作。`set_period` 留待后续，本版不接受。网关 `TX_ACK` 是发射调度结果，不是节点收到或执行证据。

## 物理层和时序

节点使用已有且实际生效的 LoRa 配置，不修改 NVS 或臆造引脚/功率。历史现场值为 470.5 MHz、SF7、BW125、CR4/5、sync 0x34；实时以节点状态与 H 网关检查为准。下行显式头、LoRa CRC 开、IQ standard（PULL_RESP `ipol=false`、`ncrc=false`），频率与目标实际监听一致；网关发射能力由 H/E2 验证。单射频半双工：节点在非发送时间监听；上行或回执发送期间不能接收，TX 完成后重新接收。网关单目标串行发送并控制重试，实测前不保证时延或覆盖。

网关从目标实际接收的 `LRN1` 取得 MAC、boot、report_seq。节点保留最近 4 次 TX 提交成功的 report_seq 与本机记录时刻（近似发射时刻，不是空口精确时间），命令的 `ttl_ms` 为 1000–60000 毫秒；引用的报告须属于当前 boot、序号匹配，且本机当前时刻距 TX 提交记录时刻不超过 ttl。无需网关和节点时钟同步。该机制限制过期命令，但不提供认证或防主动伪造；本版仅限受控地面无害命令。

## `LRC2` 命令帧：固定 48 字节，多字节整数小端

| 偏移 | 字节 | 内容 |
|---|---:|---|
| 0 | 4 | ASCII `LRC2` |
| 4 | 1 | 版本 `1` |
| 5 | 1 | `1=echo`，`2=status` |
| 6 | 2 | 总长度 `48` |
| 8 | 6 | 目标 ESP32 Wi-Fi STA MAC 原始字节 |
| 14 | 2 | 保留，必须为 0 |
| 16 | 4 | 目标当前 boot，非 0 且完全相等 |
| 20 | 4 | 引用的 LRN1 report_seq，非 0 |
| 24 | 8 | 网关生成的非 0 cmd_id，目标 boot 内唯一 |
| 32 | 4 | ttl_ms，1000–60000，从目标 report 的 TX 提交成功记录时刻计算 |
| 36 | 4 | arg：echo 为任意 u32 回显；status 必须为 0 |
| 40 | 4 | 保留，必须为 0 |
| 44 | 4 | 前 44 字节 IEEE CRC32，反射多项式 0xedb88320，初值/终值异或 0xffffffff，小端 |

## `LRA2` 回执帧：固定 48 字节

| 偏移 | 字节 | 内容 |
|---|---:|---|
| 0 | 4 | ASCII `LRA2` |
| 4 | 1 | 版本 `1` |
| 5 | 1 | 与命令相同 op |
| 6 | 2 | 总长度 `48` |
| 8 | 6 | 执行节点 MAC |
| 14 | 2 | flags：bit0=重复命令重发回执，其余为 0 |
| 16 | 4 | 执行节点 boot |
| 20 | 4 | 引用的 report_seq |
| 24 | 8 | cmd_id |
| 32 | 4 | `2=executed`，`3=rejected`；executed 同时证明目标收到 |
| 36 | 4 | echo 原 arg；status 为状态位：bit0=LoRa worker 活跃、bit1=报告角色 tx |
| 40 | 4 | 生成时单调 uptime_ms 低 32 位，仅诊断，不与网关时钟相减 |
| 44 | 4 | 同上 CRC32 |

目标不匹配、坏长度/CRC/版本/保留字段、非法操作、boot/锚点/ttl 失效一律不执行；无有效身份的坏帧不回执，避免放大。目标按 `(boot,cmd_id)` 去重，缓存 16 项，保存整条有效请求和执行结果至其 ttl 截止；相同 id 不同内容拒绝，缓存全部未过期时拒绝新命令，不提前淘汰造成重复执行。相同内容重发只重发原执行结果，不重复执行；回执排队满或发射失败只记录失败，不得谎报目标确认。网关逐目标每次一个在途，最多 3 次，间隔至少 1 秒，超时明确 unknown。实际接收窗口和网关下行支持须 H 实测。

## Wi-Fi 业务和证据

维持已有 `SR01` / `FG02` 线协议与 NVS 配置；已有 FG_DOWN/FG_RECEIPT 仅覆盖 field IP/网关业务，不把 MAC 回调当端点交付。新候选如增加普通业务端点回执，必须使用独立标识、消息序号及目标 boot，去重并限重试；旧板不支持新功能时不能报端点确认。

候选 `FLW2` 封装在 SR01 业务载荷中，保留 `FLW2` 前缀，多字节小端：0–3 magic，4 版本 1，5 类型（1 数据、2 回执），6–7 总长度，8–11 源 boot，12–15 消息 ID，16–19 目标 boot，20–25 源 MAC，26–31 目标 MAC，32 起为数据，末尾 4 字节为此前内容的 IEEE CRC32。回执无业务数据，保留原数据方向的源/目标/boot/ID；SR01 外层发送者是原目标。业务最多 124 字节，完整封装最多 160 字节。新旧板混用不能产生确认保证。

`send_reliable` 接受 `dst`、`dst_boot`、`payload_hex` 和 nonce；目标 boot 可显式提供，也可从当前双向直邻或最近收到的目标自身源帧取得。后者只是未认证的被动观测、10 秒失效，短期观测到不同 boot 时进入冲突隔离，不能推断路径中间节点的 boot；`target_boot_get` 返回来源和观测年龄，获取不到时明确拒绝。新候选最多 8 项待发、每项最多 3 次路由层成功接收提交、间隔 350 毫秒，启动后总寿命固定 1050 毫秒。本地提交失败以 100 毫秒退避且分别计数，不记作已被路由接收；无论结果都不延长寿命。路由接收不等于空口发射或目的端交付。目的端保留最多 32 项去重记录 30 秒，重复仅重发回执。目的端 `reliable_received` 表示协议层收到；源端仅收到绑定目标 MAC 和 boot 的匹配回执才发出 `reliable_delivered`，超时 `reliable_timeout` 为 unknown 并给出提交与拒绝次数。协议没有密码认证，不能据此证明消息没有被主动伪造；发送 API 返回成功也不是送达。去重有容量和时间边界，不是无限期恰好一次保证。

LoRa 恢复候选：RX/TX/重新监听驱动故障后丢弃待发送旧帧，保留当前配置和命令去重状态；依次等待 1、2、4、8 秒重新应用，连续四次失败则冷却 60 秒后再试，并在状态和事件中记录。恢复调度和命令去重的主机夹具已测；worker、驱动故障与真实射频的端到端恢复尚需进一步验证。ESP-NOW 启动失败和回调超时会进入有界冷却恢复，超时结果未知、旧包不自动重放；真实驱动回调隔离及实际收发恢复仍需验证。

新候选路由请求按来源 MAC、boot 和请求号，每个节点最多转发两条不同路径变体；这是控制开销与路径多样性的取舍，可能过滤掉可行路径。实际链路发送失败后，临时回避该下一跳 500 毫秒并至多做一次本地重发现；本地 API 失败不当作空口故障。已排队包若遇下一跳 boot 变化，标记结果未知，不向新实例重放。ESP-NOW 的 20 个 peer 槽位保留广播 1 个，最多轮换使用 19 个单播槽位，发送中不增删；真实驱动行为与动态无线网络尚待硬件验证。

C035-07 反馈默认关闭：默认构建 `MID_ROUTE_FEEDBACK=OFF`，不按缺失端点回执主动探测，保留旧路由行为；`info.route_feedback_experimental=false`。实验构建 `MID_ROUTE_FEEDBACK=ON` 时，同一路径两个不同消息各两次已提交仍未确认，才依据第一跳成功发送的有界记录检查缓存版本并发起一次有界替代路径探测；探测期间保留旧缓存，收到端点确认清除疑虑并可取消尚未完成的探测，单节点探测后冷却 3 秒。旧记录不能影响请求号或路径不同的新缓存。多次无回执可能由反向拥塞造成，实验探测仍产生控制流量；结果与边界见 `PROBE_POLICY_REPORT.md`。两种开关由不同 build_id 区分，不可混称。

沿用 LRN1，不改变已有上报解析。`LRA2` 是新增类型，网关需显式解码，不得将其计入 LRN1 邻接上报。目标 boot 必须来自真实端点上行。构建、host 夹具、PULL_RESP/TX_ACK、目标 LoRa 收件和执行回执分别记录；本文不代表功能已实现或硬件已通过。

## 数字节点编号和既有串口兼容

数字编号只是显示/部署标签，不替代 MAC 与 boot。`mid.serial.v1` 既有事件字段 `node_id` 已是 MAC 字符串，不能静默改成数字；`info`、`node_id_get`、`node_id_set` 的 `command_result` 新增 `node_mac`（MAC 字符串）、`node_number`（1..4294967295，未配置为 null）、`node_number_source`（`nvs`/`factory_map`/`unset`/`nvs_error`）和 `node_number_schema="node.number.v1"`。原 `node_id` 继续为 MAC，原 `boot_id` 与 `build_id` 保留。H 的适配器将 `node_number` 映射到其内部数值 node_id，不能把 MAC 字符串解释为编号。

`node_id_get` 使用现有 JSON nonce 合同。`node_id_set` 请求必须包含数字 `node_number`、字符串 `target_mac` 和数字 `target_boot`；二者与本机当前身份完全相等才写入独立 NVS namespace `node_ident` 的 u32 `id`。写入及 commit 均成功后才更新状态/OLED；错误明确拒绝，绝不擦除 NVS。数字 ID 全网唯一性由部署注册表检查，单板无法自行保证。NVS 无此项时仅对已登记的 A–E MAC 使用 1–5 默认映射；其他 MAC 为 UNSET。异常/损坏 NVS 标为 `nvs_error`，不猜测或静默覆盖。

上电组网读取原有 `mid_route`/`mid_neighbor` 配置；仅存在有效配置且 `autostart=true` 时自动启动。没有配置或 autostart 为 false 时不会自动入网，需部署工具明确配置群组、频道和自启；不能把固件候选本身描述成新板开机即联网。`info` 返回 `discovery_saved`、`discovery_fault`，有配置时返回 `discovery_autostart` 和 `group`。自定义数字编号目前仅显示本机；邻居表只对 A–E 使用固定数字映射，其他邻居仍显示 MAC 尾码，数字编号未在节点间广播。

新候选对 `mid_route`/`mid_neighbor` 增加独立 `lastgood` 备份，仅本组本频道出现双向邻居后写入并带 CRC；主配置损坏且备份校验通过时可读取备份，`info` 提供 `discovery_from_backup` 等状态。主配置缺失视为未配置，绝不借旧备份复活已清除配置；格式有效但群组错误不会凭无邻居自动切换。双向邻居只是单跳证据，且备份写入中断及断电原子性仍待真机验证；LoRa、静态部署和数字编号配置尚不具备同等备份。

恢复候选将两种机制分开：软件进度监测每秒观察主循环及 LoRa worker，主循环 15 秒无推进时请求软重启，LoRa 单侧无推进仅报告；另在进入 `app_main` 后配置 ESP-IDF 任务看门狗 30 秒，订阅主任务、健康任务和启用的 LoRa worker，每个任务仅在自身代码推进时重置计时。目标构建配置使用 timer-group 后端；不得把 15 秒软件检测称为硬件看门狗。连续 3 次由软件监测或任务看门狗触发的复位后，RTC 记录抑制这两类自动复位，健康任务稳定观察到推进 120 秒后尝试恢复看门狗复位。LoRa 真卡死可触发任务看门狗，前 3 次会暂时中断整机 Wi-Fi；抑制后若仍卡死则不会无限重启。现有 bootloader 的 9 秒看门狗配置未改，bootloader 阶段及其他复位来源不受本计数器完整覆盖。注册/配置状态通过 `info` 和 LoRa 状态报告；两种检测都不证明射频收发成功。所有 RTC 保留、硬件计时、真实复位、配置持久、RF 和单侧故障影响仍待 C 审查及实板验证。

分区布局的独立核验：发布包保留本次构建 `partition_table/partition-table.bin` 及其 SHA-256；另外生成 4096 字节核验镜像：原始表文件不足 4096 字节的部分用 `0xff` 补齐，记录其 SHA-256。H 在写入前用 esptool 按实际 MAC 绑定的串口只读读取 flash `0x8000` 长度 `0x1000`，将读出完整 4096 字节与发布包核验镜像作 SHA-256 比较；一致才可 app-only 写 `0x10000`，不一致停机核查，不改写分区。不得以 build_id 或固件自报代替写前真实分区表检查。明日用户连接设备后才能执行；目前只是核验方法，未实测。
