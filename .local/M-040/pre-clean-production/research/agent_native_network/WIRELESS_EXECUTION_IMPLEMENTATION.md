# 固定无线条件下的业务回放与任务执行

2026-10-26，E2-007。60次固定业务回放和18个完整任务回合已完成，等待C独立结果审查和M验收。物理参数、时间换算和实验矩阵以[来源合同](WIRELESS_SERVICE_CONTRACT.md)为准。

## 执行内容

两个入口共用E1的`WirelessBroadcastService`。`simulation/wireless_trace_replay.py`读取008阶段十个即时信息实例的原始消息，保留发布顺序、时间、正文、来源和接收者，运行3个MAC种子与FIFO/latest两种队列，共60次。它分别记录原任务结束时和队列排空后的网络账本，避免把窗口结束时尚未传完的消息计为最终丢失。回放不执行任务策略。

`simulation/heteromrta_wireless_eval.py`继承008的`DemandWorld`，复用作者固定权重和共同恢复规则。两份任务种子、三组节点/任务数量（9/15、18/30、36/60）、三种通信规则，共18回合。即时信息参照直接读取008相同目录的结果。所有任务使用CPU1、H200、内部90秒和外部120秒预算，失败和原始输出保留。

## 刷新与信息可得性

`event_fifo`按原有真实状态变化和现场事件发布；`event_latest`使用同一发布规则，只改变待发队列；`refresh_latest`另外每1模型单位（20秒）刷新一次，节点按actor/N错相。

刷新缓存只收录本节点亲自产生的完整正文。自身状态按source索引，现场消息按source和task索引。重发沿用原始字节、版本与事实生成时间，不调用生成新事实的`self_state`或`scene`，不修改本地视图，也不直接唤醒决策。现场共同见证者和网络接收者不会把别人的正文当成本人观测再发布。每次重发另记本次入队时间、原消息ID与原本地证据。

latest在服务端合并同源、同类、同对象的待发完整快照，正在发送的正文不改写。接收端继续按实际到达和版本更新缓存、构造动作mask。原有恢复计时不因刷新定时器改变抖动计数。

## 证据与指标

正式前文件位于`simulation/outputs/E2-007/20261026-00-preflight/`：`task_cases.json`固定18个配置，`preflight.json`固定来源合同、任务目录索引和脚本hash；`source-freeze.json`记录三个新脚本hash及LF检查。运行manifest另存作者源码与权重hash、旧执行器/消息服务/新无线服务快照hash、环境和预算。

七项微单测覆盖原始正文和事实年龄保持、刷新不增加本地证据/版本/决策、收到的缓存不转发、现场见证者不冒充来源、对象分离、错相定时、原任务窗口与排空区分，以及真实无线服务的接口交付。测试记录在`unit-tests.txt`。这些微单测没有执行学习策略回合。

任务统计保留完成比例、失败、超时、返回makespan以及同目录instant比值。网络统计分开记录应用发布字节、实际尝试发射时长、信道busy并集、碰撞、拒绝、替换、重复合并、接收副本、有效缓存更新。每完成任务空口成本使用实际发射时长除以完成任务数；busy比例使用信道busy除以观察窗口。队列时延从本次入队算起，事实年龄从正文原始生成时间算起。

## 三组最早动作分歧

M指定对seed5的三组比较做只读诊断，无新增任务回合。`diagnose.py`按每个actor的动作序列找首个不同选择，再按最早时刻定位；`mechanism_trace_v2.json`保存动作、mask、缓存引用、实际发布与服务事件、决策前本机状态及输入hash。v1保留为过程记录；v2用事件ID截取同一时刻的决策前状态，排除决策后的出发事件。

三组分歧之前，全局actor/branch/action序列一致；分歧处决策时刻相同、决策前本机物理状态相同，task_scene缓存版本也相同。以下ID均为0起始task/actor，action等于task ID加1，mask为true表示不可选。

1. **18节点/30任务，FIFO与latest。** actor12在t=5.381789结束task10，FIFO选择task11，latest选择task13。FIFO已收到source4的seq5（转向task13）；latest中同一seq5的`m00000050`于t=4.1451236碰撞，缓存仍为seq3。action14在FIFO被屏蔽，在latest可选。另有source5的seq3在FIFO碰撞、latest到达，诊断保留这一并存差异。该例记录了任务选择差异与缺失远端承诺状态的对应关系。
2. **36节点/60任务，FIFO与latest。** actor9在t=4.427749结束task48，FIFO选择task18，latest选择task23。FIFO中source6、12、20、22的seq3工作状态帧发生碰撞，缓存停在seq2；latest收到这四个seq3。两侧mask相同，输入中的远端执行状态不同，固定策略选择了不同任务。该例说明即使可行动作集合相同，消息交付仍会改变策略排序。
3. **36节点/60任务，latest与refresh。** actor6在t=9.208046抵达已关闭的task28，latest选择task25，refresh选择task30。source8和18已转向task30/51，其seq9在latest到达；refresh中的`m00000868`和`m00000869`于t≈9.151614碰撞，决策时尚未到下一次各自刷新机会，缓存仍为seq7。action31在latest被屏蔽，在refresh可选。刷新增加了后续恢复机会，但没有保证每次新状态都在使用前交付。

这些记录把消息结果、缓存和首次动作分歧连在一起。它们没有单独隔离每条消息对最终makespan的贡献，也未证明刷新碰撞由平均带宽占用造成；队列改变了竞争过程和各源退避抽样次数。后续若要估计关键消息的因果收益，可在相同决策前缀下进行受控交付干预，另行冻结实验方案。

## 下一步的机制入口

本轮支持把研究问题细化为：团队规模和任务并发扩大后，怎样以较少的维护开销，让影响协作选择的状态在使用前可得。候选改进可以针对完成任务后的新承诺、组队开始后的执行状态，区分高影响状态与长期未变的事实，联合决定是否更新、保留哪个待发版本和何时补发。

目前的事实依据是低平均负载下仍出现的突发竞争，以及消息遗漏怎样进入实际决策。下一轮应先验证按任务依赖选择更新和补发能否改善性能—成本折中，再扩展更大的实际业务类型与几何网络。规模增加是否导致容量瓶颈，需要由新增任务需求及其真实消息规模来检验。
