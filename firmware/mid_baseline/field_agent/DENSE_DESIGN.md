# 密集 ad-hoc 改造：机制层设计（对上一版粗糙做法的修订）

上一版（`dense` 策略）是"先止住崩溃"的应急组合，其中 S3/S4 的形式是启发式。
本文逐项给出机制、算法、参数依据、新增风险和固件落点，并明确指出哪一版不够好。

---

## S1 失败语义：从"要不要锁"到"故障分域 + 事件合并"

### 现在的粗糙做法
`lock_on_overflow=False` + 队列 16→64。等于"不再因为溢出杀节点，并把缓冲加大"。

**为什么粗糙**：队列深度是症状不是病因。真正的病因是**每一帧、每一个事件都单独入队**：
30 个邻居每 2.5 s 一个 hello ≈ 12 帧/s 进队，每帧还要拼一条 JSON 输出。
把 16 改成 64 只是把爆炸推迟 4 倍时间。

### 机制
1. **邻居状态合并（coalescing）**：ND 不需要"hello 的队列"。
   收到 hello 只更新 `pending[peer] = latest_seq`（32 个字节的位图/序号），
   主循环按帧处理这张表。29 个邻居的突发 hello 从 29 个队列项压成 1 次状态扫描。
2. **按类别分队列**：
   | 类别 | 结构 | 满时策略 |
   |---|---|---|
   | 邻居状态 | 位图，无队列 | 不可能满 |
   | 路由帧（RREQ/RREP） | 环形 32 | **丢最旧**（泛洪是幂等的，旧帧价值最低） |
   | 业务数据 | 环形 32 | 丢最旧 + 计数（业务本身无重传，不做假交付） |
   | 主机命令 | 小队列 8 | **不丢**（丢了主机就失去控制） |
3. **故障分域处理**：
   - RX 积压 → 按上表丢，只计数；
   - 发送回调丢失 → 只让**该邻居的链路样本**失效，不动 ND 表、不动路由表、不动射频；
   - 射频驱动连续失败（连续 N 次 `esp_now_send` 返回非 OK）→ 这才是"射频坏了"的判据，
     走 `close_radio()` + 指数退避（1/2/4/8 s，**上限 60 s 而非三次就死**）；
   - 永不"每 boot 三次即永久锁"：反复失败的节点以 60 s 周期重试，并在 `stats` 里标 `degraded`。

**关键区别**：原设计用"回调超时"推断"射频不可信"；正确做法是**只把回调当链路证据**，
用驱动返回值判断射频健康。这两件事被混在一起，才有了"一次丢帧就整机下线"。

### 固件落点
`app_main.c` 的 `inputs` 队列与主循环、`callback_drops` 路径、`radio_heal()`。
新增 `pending_nd` 位图与四个独立队列。

## S2 容量：从"乘 4"到"按密度与内存推导 + 淘汰策略"

### 现在的粗糙做法
邻居 8→32、路由 8→32、去重 32→128、待决 8→16。

**为什么粗糙**：数字没有推导；而且**淘汰策略是"找第一个空槽"**，满了就静默丢弃。
消融已经证明：只放大表、不做泛洪抑制，RREQ/次发现从 262 涨到 869、丢帧 1.8 万——**负优化**。

### 机制
1. **尺寸按部署推导**：
   - `nd_peers`：目标密度下最大邻居数 + 余量。30 节点、通信半径 120 m、圆盘 R=147 m 时
     理论最大 29，取 32；若目标是 60 节点，需按同样的几何重新算（不是线性放大）。
   - `sr_routes`：由**并发目的地数**决定，不是 N。业务 roster ≤8 + PC 1 + 重传路径若干 → 16 够用，
     32 只为余量。
   - `sr_seen`（去重窗口）：必须覆盖**一次泛洪的生命周期** = TTL × 每跳处理时延 + 轮次间隔。
     N=30、TTL=4、一次泛洪 ~30 帧、并发 2 轮 → 64 起，取 128。
   - 内存核算：`free_heap` 实测约 103 KB，`sr_node` 现 18 KB；32/32/128/16 约 33 KB。
     **必须在 `stats` 里同时报 `free_heap` 与 `minimum_free_heap`**，并把水位写成构建期断言。
2. **淘汰策略**（比尺寸更重要）：
   - 邻居表：**先淘汰已过期（> ND_LOST）的，再淘汰最久未听到的**；
   - 路由表：**先淘汰已过期，再 LRU**；
   - 去重表：环形覆盖写（FIFO 即可，因为有效期短）；
   - 增加**负缓存**（不可达目的地，16 项，TTL 30 s），避免反复泛洪同一个不可达目标。

## S3 去掉 ACK：从"互相听到 hello"到"任意帧 + 发送回调"

### 现在的粗糙做法
双向 = 双方近期互相听到 hello。ACK 帧全删。

**为什么粗糙**：
- 它把"我方→对方"的证据也建立在**对方的广播**上，确认要等满一个 hello 周期（2–8 s）；
- 它无法区分"对方能听到我"与"我能听到对方"的强弱；
- 更关键：**它忽略了已经存在的一手证据**。

### 机制
ESP-NOW 的**单播发送回调就是 MAC 层 ACK 的结果**：`tx_link_ok` 直接证明"我这一帧到达了 peer"。
所以：

1. **任意帧更新 `heard[peer]`**（不只 hello）：数据、RREQ、RREP 都是"对方存在"的证据。
   这样 hello 只承担"我很闲、我还活着"的角色。
2. **单播发送回调更新 `tx_ok[peer]`**：这是"我方→对方"的真实证据，零额外帧。
3. **双向判定**：`t - heard[peer] < T_heard` 且 `t - tx_ok[peer] < T_tx`。
   对从未单播过的邻居，"我方→对方"未知——但**只有在要把它用作下一跳时才需要知道**，
   而那一刻的 RREQ 转发/数据发送本身就会给出答案；失败就换下一个候选，并记一次负样本。
4. **按需探测（兜底）**：若某邻居 T_confirm 内既无 `heard` 也无 `tx_ok`，而我们确实要用它，
   发 1 个单播探测帧（不是对所有 hello 都回 ACK）。ACK 总量从 O(N²/period) 降到 O(实际使用)。

**收益（相对"互相听到"版）**：确认时延从"等一个 hello 周期"降到"一次单播往返"；
且双向证据只在真正需要时获取，平时零成本。

**新增风险**：广播 RREQ 的转发不产生 `tx_ok`（广播无 MAC ACK），所以中继候选的
"我方→对方"仍要等一次单播。可用 RREP 回程顺便确认。

## S4 hello 调度：从"按度数拉伸周期"到"按检测需求定周期 + 抑制 + 错峰"

### 现在的粗糙做法
`period = 8000 - (8000-2500) * min(1, 8/deg)`。纯经验式，且把"密度"直接映射成"周期"。

**为什么粗糙**：
- 周期应该由**失联检测需求**决定：`T_hello ≈ T_lost / K_miss`（例如 12 s / 3 ≈ 4 s）；
  密度不应该改变这个需求；
- 密度真正影响的是**碰撞与同步突发**，而这一版没有处理；
- 周期拉长会同时拖慢"新邻居发现"和"失联判定"，没有区分这两者。

### 机制
1. **周期由需求定**：`T_hello = clamp(T_lost / K_miss, 2 s, 6 s)`，默认 4 s；
   若表内邻居数 < 4（小规模/冷启动）降到 2 s 以加快收敛。
2. **抑制规则**：如果过去 `T_hello/2` 内我方对该邻居已经发过任意帧，则该邻居"知道我"，本周期不需要喊；
   广播无法逐邻居抑制，所以规则作用于**全局**：过去 `T_hello` 内已发送 ≥ M 帧则跳过本次 hello。
   配合 S3 的"任意帧更新 heard"，这是安全的。
3. **错峰**：`hello_at = epoch*T_hello + hash(node_id, epoch) % T_hello`，
   避免所有节点在 epoch 起点同时广播（仿真里没建模，实机会撞）。

## S5 路由预热：从"取消"到"需求驱动 + 滞回"

### 现在的粗糙做法
`warm=False`，直接删掉周期预热。

**为什么粗糙**：消融显示它让收敛 7.2 s→4.5 s，但这是"删掉了一个负优化"，不是"设计了一个正确策略"。
密集场景下预热不是无用，而是**必须与真实需求挂钩**。

### 机制
1. 每个目的地维护 **demand EWMA**（近期发送尝试/秒）。
2. 仅当 `demand > 0` 且该目的地**无有效路由**时发起预热查询；
   路由存在且剩余 > 1/2 缓存寿命时不做任何事。
3. 失败用**指数退避**（2/4/8/16 s），并写入**负缓存**（30 s 内不再泛洪该目标）。
4. 每节点**同时在途的预热轮次 ≤ 1**，且可被真实业务请求抢占。

## S6 泛洪控制：从"扩展环 + 按源去重"到"有界转发 + 沿途应答 + 令牌桶"

### 现在的粗糙做法
TTL 2→3→4 逐轮；去重键 `(源,请求)`；每节点 500 ms 全局限速。

**为什么粗糙**：
- 只做了**去重**，没做**转发抑制**：密集图里每个节点仍会转发一次，一次泛洪仍是 O(N) 帧；
- 500 ms 是**全局**闸门，会饿死合法的并发发现；
- 没有"沿途应答"：目的地在 3 跳内，却让泛洪扩散到 4 跳。

### 机制
1. **去重**：`(origin, req)` 的定长哈希环（TTL = 泛洪生命周期），O(1) 查表。
2. **有界转发**：为每个请求维护**总转发计数上限**（如 `4 × 期望跳数`），达到即停止扩散；
   同时按"是否更接近目的地"抑制：只允许路径长度 ≤ 当前最短已知路径的节点转发。
3. **沿途应答（gratuitous reply）**：中间节点若持有该目的地**未过期**的路由，直接回 RREP，
   不再转发。这一条通常能砍掉一半以上的泛洪半径。
4. **扩展环**：TTL 2 → 4 → 6（二分增长），任一轮成功即止；失败走负缓存。
5. **限速**：**每邻居令牌桶**（如 2 帧/s/邻居）+ 全节点总桶（如 10 帧/s），
   而不是单一 500 ms 闸门。

## 横切问题（上一版完全没碰）

1. **全局单在飞发送**：一个 `waiting` 标志 + 1 s 超时。30 节点时它成为吞吐天花板，
   也让"回调丢失"的爆炸半径变成整机。应改为 **per-peer 在飞窗口（1–2）**。
2. **没有拥塞信号**：应暴露队列水位、单位时间丢帧、RREQ 速率，并用它们反压 hello/泛洪速率。
3. **没有信道接入**：固件直接 `esp_now_send`，没有退避。密集场景必须加 CSMA 退避。
4. **没有移动性处理**：ND_LOST=12 s 在 10 m/s 下是 120 m 的滞后，需要更快的几何感知
   （或至少按速度自适应）。

## 修订后的实施顺序

| 顺序 | 内容 | 为什么先做 |
|---|---|---|
| 1 | S1（合并且分队列 + 故障分域） | 决定节点在不在；且是所有后续测量的前提 |
| 2 | S6（有界转发 + 沿途应答 + 令牌桶） | 决定泛洪会不会打穿处理能力 |
| 3 | S3（任意帧 + 发送回调做双向证据） | 一次性删掉 O(N²) 的 ACK，且比"互相听到"更准 |
| 4 | S4（需求定周期 + 抑制 + 错峰） | 控制面继续降，且不牺牲检测时延 |
| 5 | S2（按密度推导尺寸 + 淘汰策略 + 负缓存） | 必须在 S6 之后，否则放大泛洪 |
| 6 | 横切：per-peer 在飞窗口、CSMA 退避、拥塞反压 | 吞吐与真实空口行为 |

## 仿真还缺什么

- **碰撞与隐藏终端**：现在的模型是纯串行化，任何"丢帧 0"都不能外推；
- **业务流量**：没有端到端交付率与排队时延；
- **移动**：没有拓扑变化下的重建成本；
- **多速率/多信道**：单信道 1 Mbps 是假设。

在这些补齐之前，本文的算法结论只能作为**方向性**依据，不能作为验收。
