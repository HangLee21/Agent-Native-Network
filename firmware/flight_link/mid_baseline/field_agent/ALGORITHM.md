# 三平面算法总纲（2026-11-12 整理）

本文是当前**全部算法逻辑**的单一入口：状态、报文、时序、判决、失败语义、规模规则与落地状态。
每个条目都标注实现状态：

- 【板】已在实板运行
- 【编】已编译进镜像、尚未烧录
- 【仿】只有仿真，未进固件
- 【未】尚未实现

---

# 0 系统全景

```
        ┌─────────────── LoRa 控制层（独立 PHY，470 MHz）───────────────┐
        │  网关(8 上行接收 + 1 下行)  ←── LRN1 邻居表快照 ←── 各节点     │
        └──────────────────────────────────────────────────────────────┘
                                    ▲ 内容来源
        ┌────────────── Wi-Fi 控制面（2.4 GHz，channel 11）─────────────┐
        │  ND：hello/ACK → 三态邻居    SR：RREQ/RREP/RERR → 源路由表     │
        └──────────────────────────────────────────────────────────────┘
                                    ▼ 服务
        ┌────────────── Wi-Fi 数据面（同一 ESP-NOW 信道）───────────────┐
        │  业务包 → 逐跳单播转发 → 目的端 rx_local（唯一交付判据）        │
        └──────────────────────────────────────────────────────────────┘
```

三层共享同一份**邻居状态**；LoRa 与 Wi-Fi 物理隔离，互不阻塞，只通过"内容"耦合。

# 1 自启动 【板】

没有任何主机命令，上电即恢复全部功能。

## 1.1 启动顺序（app_main）

```
UART0 @460800 8N1
  → nvs_flash_init
  → 读 STA MAC，boot = esp_random()|1
  → field_boot()            读 field_agent/cfg，恢复发生器
  → lora_ref_init(self,boot) 读 lr_ref/cfg，建 LoRa worker，按保存角色起
  → OLED、串口读任务、发 boot 事件
  → discovery_load()         读 mid_route/cfg → group/channel/autostart
  → deployment_load()        读 mid_deploy/profile
  → 若 autostart：discovery_start()（Wi-Fi STA + ESP-NOW + ND/SR 初始化）
  → 主循环：radio_heal → field_tick → lora_ref_tick → 串口命令 → 业务泵
```

## 1.2 三个独立的自启动开关

| 通道 | NVS | 字段 | 生效点 |
|---|---|---|---|
| Wi-Fi/ESP-NOW | `mid_route/cfg`（12 B, `NDc1`） | group/channel/autostart | `discovery_start()` |
| 离线转发表 | `mid_deploy/profile` | autostart | `deployment_start()` |
| LoRa | `lr_ref/cfg` | role/PHY/period/`start_on_boot` | worker 立即应用 |
| 业务发生器 | `field_agent/cfg`（72 B, `FA01`） | min/max/len/roster/`start_on_boot` | `fa_apply()` |

## 1.3 实测
RTS/EN 复位后零命令：五板 `mode=active`、`radio=true`、`group=31`、
LoRa 角色 A=rx / B–E=tx、`frequency_hz=470000000`、`requested=applied=1`。
**未验证**：真正拔电（非复位）自启。

# 2 Wi-Fi 控制面：邻居发现（ND）【板】

## 2.1 报文

`kind=1, ttl=1, size=17`，body：`"ND01"`(4) + group(4) + type(1) + target(4) + echo(4)
- `type=1` hello（target=echo=0）
- `type=2` ACK（target=被确认的 boot，echo=hello 的 seq）

## 2.2 状态机

| 状态 | 判据 |
|---|---|
| `lost` | `now - seen ≥ ND_LOST_MS (12 s)` |
| `heard` | 收到过 hello，但未双向 |
| `bidirectional` | `confirm && now - ack < ND_CONFIRM_MS (9 s)`，且 `now - seen < 12 s` |

- hello 周期 **2–3 s**（`2000 + rand%1001`），每板独立错相。
- 收到 hello 立即回 ACK；**同一 peer 500 ms 内最多一次**（防 ACK 风暴）。
- **只有 bidirectional 才能作为下一跳**——单向链路永不进入路由。

## 2.3 容量 【编】
`ND_PEERS` 8 → **32**（30 节点下平均度约 14，最坏 29）。

## 2.4 移动自适应（仅仿真）【仿】
`T_lost = clamp(0.3·R/v, 2 s, 12 s)`，`T_hello = T_lost/3`。
20 m/s 时 2 s / 0.7 s；静止时 12 s / 4 s。固件没有速度输入，未实现。

# 3 Wi-Fi 数据面：源路由与转发 【板】

## 3.1 报文

`SR01` 定长头 **60 B** + 载荷 ≤160 B（总 ≤220）：

| 字段 | 字节 | 说明 |
|---|---:|---|
| magic | 4 | `"SR01"` |
| group | 4 | 组号，不匹配直接丢弃 |
| type | 1 | 1 RREQ / 2 RREP / 3 DATA / 4 ERROR（+4 为服务变体） |
| n / index / ttl | 3 | 路径长度 / 当前跳 / 剩余跳 |
| boot / seq / request | 12 | 原始源身份与请求号 |
| dst | 6 | 最终目的 MAC |
| path | 30 | **5 个节点 × 6 B** |
| payload | ≤160 | |

## 3.2 发现：RREQ → RREP

```
源 s 要发给 d，且无有效路由：
  分配一个 round(request=++seq, deadline=now+1500ms)
  广播 RREQ{path=[s], dst=d, ttl=4}
  每个转发者：追加自己到 path；TTL--；TTL>0 继续广播
  目的 d 收到：翻转成 RREP，index=n-2，沿 path 反向逐跳单播
  s 收到 RREP：登记候选；首个候选后再等 200 ms；窗口结束选最短一条装表
```

- **去重键** `(boot, request, path)`，窗口 `SR_SEEN` 32 → **128** 【编】
- 路由缓存 **10 s**，并用 `first_boot` 绑定下一跳的启动代数（对端重启即作废）
- 最多 **5 节点 / 4 跳**（`path[5]`、`ttl=4`）——见 §7 的实测讨论

## 3.3 转发与排队

- 每跳**单播**（ESP-NOW 单播有 MAC ACK），`txq` 深度 16，**同一时刻仅 1 个在飞**
- 发送后 1 s 未收到回调 → 判本地失败
- 数据包到达目的端：按 `(origin, boot, seq)` 去重（64 项），**只认 `rx_local` + payload 一致**

## 3.4 失败语义

| 事件 | 处理 | 状态 |
|---|---|---|
| 首跳不再双向 | `invalidate(self, peer)`：作废所有经过该边的路由 | 【板】 |
| 数据帧某边转发失败 | 回 `SR_ERROR` 给源，源作废该路径 | 【板】 |
| 本地数据首跳失败 | **一次**本地重发现（`retried[8]` 环，防风暴） | 【板】 |
| 等待路由超时 | `SR_QUEUE_MS = 250 ms` 后丢包并计数 | 【板】 |
| 输入队列溢出 | 丢帧+计数，不停射频 | 【板】（v3） |
| 发送回调 1 s 未到 | 停射频 → 3 s 隔离 → 重建 ESP-NOW；每 boot 最多 3 次 | 【板】（v3） |

## 3.5 容量与限速 【编】

| 参数 | 旧 | 新 |
|---|---:|---:|
| `SR_PEERS` / `SR_ROUTES` | 8 / 8 | **32 / 32** |
| `SR_SEEN` | 32 | **128** |
| `SR_PENDING` | 8 | **16** |
| 发现令牌桶 | 无 | **burst 4，每 250 ms 补 1 个** |

令牌桶限的是**速率**，不是单次泛洪的覆盖——固定转发上限实测会毁掉可达性（§8.1）。

# 4 LoRa 控制层：拓扑上报 【板】

## 4.1 语义

周期性地把**本节点的 1 跳邻居表**送给网关。它是**快照**，丢一帧只意味着拓扑旧一点，
不承载业务，因此没有 ACK、没有重传、没有中继。

## 4.2 帧格式 LRN1

```
44 B 头： "LRN1" | header_len=44 | row_len=20 | flags | n
         observer MAC(6) | observer boot(4) | report_seq(4) | snapshot_at_ms(8)
         group(4) | visible_rows(1) | reserved(1) | period(4) | tx_delay(4)
n × 20 B: peer MAC(6) | peer boot(4) | state(1) | valid_flags(1)
          seen_age(2) | ack_age(2) | Wi-Fi RSSI(1) | rf_age(2) | Wi-Fi channel(1)
CRC32(4)
```
- 行数 ≤8；**无邻居也发空表**（保证 `report_seq` 连续，主机可检测缺口）
- 序号耗尽即停发，不回卷
- `state`：0 失效 / 1 听到 / 2 互证；方向为 `peer → observer`

## 4.3 寻址原理

帧里**没有目的地址**。谁配成 `role=rx` 且 PHY 六参数一致，谁就收；
串口事件里的 `gateway_id` 是**接收方自己填自己的 MAC**。
所以网关是**配出来的**，不是选出来的；换网关只改角色，不改协议。

## 4.4 PHY 与时序

`470 MHz / SF7 / BW125 / CR4-5 / 0 dBm(标称) / sync 18 / preamble 8`，
周期 **10 s ± 250 ms**，首相位按 `(boot ^ MAC)` 打散。

## 4.5 规模规则（8 上行 + 1 下行）

设每信道发送端 `m = ceil((N−1)/C)`、单帧 ToA `τ`、目标占空 `ρ`：

> **`T ≥ m·τ / ρ`**。208 B 在 SF7/BW125 下 `τ = 328 ms`。

| 条件 | 结果（仿真） |
|---|---|
| 单信道，30 节点，10 s | 占空 95%，送达 **5.7%** |
| 8 信道，30 节点，10 s | 占空 11%，送达 **65%** |
| 8 信道，25 s | 占空 4.9%，送达 84% |
| **8 信道 + 调度化上行，10 s** | **送达 95%**，下行占空 1.1% 【仿】 |

**调度化上行**（用那 1 条下行每超帧广播时隙表）把"周期"与"送达率"解耦：
一旦允许多跳并发，周期只由拓扑新鲜度决定。漏收调度帧的节点在超帧尾部
15% 的竞争窗口退化为 ALOHA，实测漏收率 2% 时仍保持 0.95。

# 5 判据与证据纪律

全系统只有一条交付判据：**目的端 `rx_local` 且 payload 字节相同**。
`tx_link_ok` 只代表本地链路成功；`submitted`/`tx_done` 只代表芯片发出。
所有结论都附带原始 `native.jsonl`、逐板 `raw.bin` 与 `result.json`。

# 6 规模设计规则（N=30 已验证）

| 项 | 规则 | 依据 |
|---|---|---|
| 邻居/路由表 | ≥ 2× 平均度 | N=30 平均度 14 → 32 |
| 去重窗口 | ≥ 一次泛洪的总帧数 | ~30 帧 × 2 并发 → 128 |
| 发现限速 | 令牌桶，不用固定转发上限 | §8.1 |
| LoRa 周期 | `T ≥ m·τ/ρ`，ρ 取 0.05 | §4.5 |
| 跳数上限 | 需 ≥ 网络直径；紧凑编队 3 跳足够 | §7 |

# 7 跳数上限：4 跳够不够

| 队形（30 节点） | 直径 | hop=4 | hop=8 | hop=32 |
|---|---:|---:|---:|---:|
| 紧凑编队 | 3 | 0.94–0.97 | 0.95–0.96 | 同 |
| 稀疏 | 6 | 0.13 | 0.15 | 0.16 |
| 长链（链路良好） | 29 | 0.224 | 0.255 | 0.280 |
| 长链（链路勉强） | 29 | 0.054 | — | 0.059 |

**结论**：4 跳对紧凑编队不是瓶颈；长链的瓶颈是**路由建立时延 vs 250 ms 待发窗口**
与逐跳损耗累积，**不是跳数上限**。提高上限需改定长头（每跳 +6 B），性价比低。

# 8 已否掉的方案（负面结果，保留以防重复踩坑）

## 8.1 固定转发上限
每个 RREQ 最多转发 8 帧 → N=30、5 m/s 时 PDR **0.909 → 0.642**（截断 10,281 次）。
密集图里一次泛洪本就要几十帧。**改用令牌桶限速。**

## 8.2 沿途应答（gratuitous RREP）
RREQ 降低 32%，但 PDR **0.911 → 0.836**。因为固件在窗口结束时按最短候选选路，
而仿真中多个 RREP 互相覆盖，收益无法确认。**暂不采用。**

## 8.3 广播重传救长链
给 RREQ 加 3 次重传，长链 PDR 仅 0.054 → 0.062。**链路本身在极限，重传无效。**

# 10 已知短板

1. **LoRa 在镜像里仍是 ALOHA**：30 节点 8 信道 10 s 周期送达约 65%，调度版未上板。
2. **长链首包丢失**：待发窗口 250 ms 小于远距离发现时延。
3. **Wi-Fi 无 CSMA/碰撞模型**：所有 PDR 都是乐观上界。
4. **节点退出后**：PDR 0.70–0.77 已接近理论上限（目的地消失），无需"修复"。
5. **RAM 增加约 11 KB**（表容量），未在实板确认 heap 水位。
