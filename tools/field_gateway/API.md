# PC terminal HTTP v1

The HTTP service binds loopback, default port 8791. It serves the existing field map assets and `/api/v1/state` and `/api/v1/timeline` from the observation State. The UDP radio-entry adapter is separate. No serial device is opened.

`GET /api/pc/status` returns `ok`, `schema_version:1`, `pc_id` (nonzero uint32), `pc_session` (`pc_boot` is a local alias), `pc_address` (`pc:` plus eight lowercase hex digits), reserved `pc_service_mac`, `instance_id`, `connected`, `max_payload_bytes`, `serial_access:false`, `entries`, `entry`, `wireless`, `counters`. `entries[]` contains `node_id`, `boot_id`, `address:[IPv4,port]`, `connected`, `lease_remaining_ms`, `source`, native `status` counters. Each lease is independent. `entry` is the last selection diagnostic, nullable. `wireless.entry_selection` is `dynamic_multi_entry`; no user entry selection is required. `connected` only means an IP entry exists. A remote destination still needs fresh route evidence. E1 field.ip.v2 application limit is 128 bytes; unknown capability blocks sends. Empty entry lists are valid.

`POST /api/pc/send` accepts exactly `{request_id,dst,payload_hex}`. `request_id` has 8–64 ASCII letters, digits, `_` or `-`. Destination is the lowercase final board MAC. Payload hex is even-length and at most the reported cross-network byte limit; zero bytes is permitted by the PC interface. Content type is `application/json` and `Origin` must equal the loopback API origin. A repeated ID binds the same destination/bytes and returns its original record without another business send. Routes are selected by the backend; this body has no entry or path argument.

A successful local call returns `{ok:true,record:{...}}`. The record includes `request_id`, original `request`, `pc_id`, `pc_boot`, `transaction_id`, `entry`, `state`, `entry_accepted`, `destination_received`, `pc_received:false`, `delivery_status`, timestamps and optional `receipts`/`error`. Its frozen `entry` includes node/boot/address, `basis` (`direct_ip_registration` or `board_route_evidence`), `hops`, remaining evidence lifetime, raw evidence and `transport` (`wifi_ip` or `wifi_ip_then_espnow`).

`state:outcome_unknown` means a local durable reservation exists but entry acceptance is unconfirmed. `entry_accepted` is source admission. `destination_received` needs an actual correlated destination receipt and original byte comparison. No sender receipt adds a PC inbox item. Reconnection and entry failover do not automatically replay an unknown message. Later new messages use the currently valid entries.

`GET /api/pc/requests/<request_id>` returns `{ok:true,record}` or HTTP 404. HTTP 400 means invalid fields/ID reuse/oversize payload; HTTP 403 means a write lacks the correct local origin; HTTP 503 with `{ok:false,business_submitted:false,error}` means no entry or no fresh route evidence was available before any business datagram. A call can take the finite route-query window; clients should allow eight seconds. When submission happened but acceptance is unknown, the durable record is returned with the same immutable ID.

`GET /api/pc/inbox?after=0` returns `{ok:true,records,cursor,oldest_cursor,truncated,retained_limit:1024,scope:pc_actual_receive_only}`. Each received record contains `origin`, `origin_boot`, original radio `seq`, logical `transaction_id`, `pc_id`, actual forwarding `entry_id`, `payload_hex`, logical PC `dst`, `received_at`, `pc_received:true`, `delivery_status:pc_received` and the raw wireless record. Logical source/boot/transaction deduplicates repeated forwarding through different entries. A cursor gap remains explicit. Reading does not consume another client's inbox.

`GET /api/pc/events?after=0` returns `{ok:true,events,cursor,oldest_cursor,truncated,instance_id}`. Each event has `kind`, local `received_at`, `cursor` and its record/raw evidence. Reset the event cursor after `instance_id` changes. Board entry admission, destination receipt, actual PC inbox, duplicate receive and wireless report are separate event kinds.

The map starts empty. Only actual received board/remote observations may add nodes and edges; IP entry registration is not proof of an ESP-NOW link. Missing GPS remains null. Original RF direction, source, age and cache gaps remain visible. UDP fixture reports must explicitly identify their RF source as simulated.

E2-030 adds `status.telemetry` with `map_outcomes`, `recent_rejections`, `map_nodes`, producer `native_report_only` and `post_reports_supported:false`. `wireless.decoded_event_types`, report counters and `wireless.event_cursors` expose the stages before State. These additive fields appear only after the updated process is loaded. `POST /api/v1/reports` remains 404 on the PC terminal; the standard 8790 observation gateway is a separate State. See `deploy/field_gateway/TELEMETRY.md` for a passive GET-only reader usable by H's existing controller without a PC restart.
