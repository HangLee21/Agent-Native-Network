# 协作通信baseline筛选

当前任务调度主线见[2026-10-23筛查结果](TASK_SCHEDULING_SCREEN.md)，优先复现HeteroMRTA及其原始基线。下表保留通信层构件。

2026-10-22。筛选原则：每项明确控制变量、读取信息与可执行范围；先比较固定运动下的信息交付，再扩展移动协同。

|来源/构件|原文依据|本轮位置|后续实现工作|
|---|---|---|---|
|独立本地执行|任务能力对照|直接实现，本地90秒与辅助后10秒均为扫描输入|扫描能力互补强弱|
|即时网络|通信参考|保留观测排队与服务时间|用于分解网络等待|
|FIFO缓存转发|标准工程对照|实现固定逐跳路径、断连缓存|增加丢包/ACK|
|ACHORD P29|§III-B数据分层和传输、§IV通信感知协同|实现请求/结果优先这一构件|核对原有ARQ、流控、分层参数再做系统级对照|
|MOCHA P28|§III分布式同步、§IV机会接触实验|on_demand测量是否推送无关背景；缓存转发为共同底座|实现版本同步/缺失数据请求和gossip；当前构件名称不冒用MOCHA|
|Bundle Protocol v7|RFC9171 §3、§5存储与转发服务|用于明确断连缓存模型|选具体DTN路由算法后做路由对照；BP本身是协议规范|
|iHERO P37|官方任务请求与返回机制|任务请求接口参考|阅读完整算法后加入移动条件对照|
|MACE P38|§III–IV通信窗口与沿途探索|移动固定阶段保留为后续对照|引入接触恢复时比较顺路任务收益|

本轮priority仅使用全体策略都可见的消息类型，不读取未来任务收益或环境真值。背景地图被设为当前辅助动作不消费的数据，因此on_demand负责量化业务筛选，不与priority收益混算。AoI/latest-only适合可覆盖的状态流；请求和对应结果先按独立任务保存，后续用显式版本判断可替代关系。EDF需要任务提供期限，首轮采用任务完成时间目标。

原文入口：[ACHORD](https://arxiv.org/html/2206.02245)、[MOCHA](https://arxiv.org/html/2309.15975)、[RFC9171](https://www.rfc-editor.org/rfc/rfc9171.html)、[iHERO](https://www.roboticsproceedings.org/rss20/p115.html)、[MACE](https://arxiv.org/html/2609.12502)。ACHORD/MOCHA沿用前期§III–IV核查，本轮重新确认来源与机制定位。RFC是标准资料，论文主表保持38篇。
