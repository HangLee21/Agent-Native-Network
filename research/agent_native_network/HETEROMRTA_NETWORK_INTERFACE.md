## 2. 信息从哪里来

### 公共初始资料

任务位置、需求、作业时长、机器人能力/速度/驻地及空的初始执行状态作为任务前共同 catalog。它们来自与 E1-002 相同的随机实例生成器，并用初态 SHA256 校验。该预装假设只适用于当前静态任务入口；不把它扩展为运行时免费发现新任务。

### 唯一运行时发布内容

只有原 `agent_step` 接受某机器人命令后，该源发布一条自身意图正文：`source, seq, generated_at, action, arrival, departure, travel_time, travel_dist, decision_step`，另有类型/schema。没有发布 `task_dic`、全体机器人状态、全局 `feasible_assignment` 或其他节点的 `assigned`。

这里的到达/出发参数是原执行器下发给该机器人的计划，不是提前获得的实际完成观测。每源序号连续递增，意图是不可任意覆盖的事件。传输层保留每条正文，不使用 latest-only 删除仍有派生作用的历史意图。

### 接收端派生

每个接收者持有独立深拷贝，原环境后续变化不改变该副本。正文到达后，副本更新该源的路线、预计到达和目标，按原 `task_update/agent_update` 规则从已知意图推导成员、剩余能力、可行组队计划、预计开始/结束和分配状态。`agent_observe`、mask 和 `all_feasible` 控制分支全部在副本中读取。

`feasible_assignment` 在这里表示从接收意图推导的预约计划。原代码在计划成员能力足够时就预定未来作业时间，它不等于现场已经组队完成，也不等于真实完成报告。缓存不会把派生计划冒充外部传感事实。

### 可见性和时序

- 原同一时刻按随机 `release_agents` 顺序逐个执行；每个微步发布后立即排空零延迟正文，再比较下一个节点，保持原因果顺序。
- 延迟正文在其规定到达时刻进入副本；观测时只推进本地显示时间。原 `check_finished` 的 timer checkpoint 作为固定轨迹诊断输入重放，明确记在 `checkpoints.json`。
- 头部不推进正文版本；重复正文幂等。源内乱序先缓冲，缺失前序时后续事件保持阻塞；不假定缺包最终必然补齐。
- 本轮无真实 ACK 协议。`delivery_events.json` 是仿真观测日志，不作为发送端免费确认反馈。头/body、入队/送达的边界已测试，ACK 延迟、丢失和反馈控制留待下一层。

因此本层可验证“catalog＋已送达意图＋给定时钟检查点→缓存特征”，实际任务轨迹仍保留原全局调度和接受/拒绝规则。这是固定轨迹信息干预，独立副本不等于已经完成去中心化执行。

## 5. 下一阶段的具体实现任务

1. **因果运动与任务物理层。** 维护真实网络位置与出发时间；对当前7条回溯路径统一修正。物理任务开始/完成由实际到场能力满足决定，节点只通过本地可感知事件或消息获知。
2. **本地事件议程。** 用自身运动计时、已送达事件和本地等待计时器产生决策；移除原 `next_decision/agent_update` 的全局免费唤醒。原 `agent_step` 的全局可行拒绝须改成已定义的请求/回应或到场发现机制，不能即时给远端失败反馈。
3. **事件来源与协作计划。** 继续保留节点自产意图；新增到达、撤销、任务现场开始/完成事件时明确观察者和发布者。计划可行性与实际完成事实分别存储，验证遗漏/乱序不会被环境真值补全。
4. **统一网络服务。** 为控制、意图和任务事件配置同一序列化、队列、实际服务与反馈，先做因果适配后的即时信息对照，再逐项加入延迟/丢失/计费。此后才有受限信息闭环的任务完成与成本曲线。
