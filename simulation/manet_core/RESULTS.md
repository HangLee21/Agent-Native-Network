# E1-031 算法、证据与下一步

更新时间 2026-11-14；执行状态以 `coordination/tasks/E1-031.md` 最新记录为准。目标为30节点动态自组网通信，用户尚未给出业务频率、载荷、时限与可接受丢包率。本文结果均是合成无线模型，不等同实板或飞行结果，E1自检不替代E2/C独立复核。

## 已实现的实验基线和候选

`aodv.c/.h` 是有界的自定义逐跳协议，依据 [RFC 3561](https://www.rfc-editor.org/rfc/rfc3561) 实现按需RREQ/RREP/RERR、目的序号和扩环搜索；`ALGORITHM.md` 记录实现边界。它不是完整 AODV，也不与标准IP报文或旧项目 v1 互通。采用自定义 v2 头32字节、业务最多160字节。当前 `adaptive/` policy1是可用新鲜路由的中间答复基线，policy5在本地观察到重复RREQ压力后限制转发；控制帧和业务帧的模型空口占用均计入。

一次自检发现定时器会在RREQ因限速尚未发出时提前扩环；现已修复并增加夹具。旧数据保留原快照，不以旧版本的通过替代新版本。`43-deferred-recheck` 中三个普通负载场景的30条修复前后事件流完全一致；高负载比较中0/10一致，说明部分场景可能受影响。

## 丢失和拥塞的解释边界

`21-reach-reorganize`、`22-reach-crossing` 的几何诊断与相应旧快照样例的其他事件一致。重组示例中约84%的成熟业务在提交瞬间没有合成几何路径；少量后来仍按时收到，表明不能把瞬时分区当永久断连或唯一丢因。交叉示例中提交时几何2跳、3–4跳业务1秒按时率分别约55%、29%，说明有几何路径仍可能失败。真实 RF 路径、持续连通和干扰未测。

旧 `23-hop-cap` 中8/16/32跳比较显示更高跳限同时增加控制负载并未改善1秒率；由于定时器随后修复，它只是旧版诊断。最新同源 `49-deferred-hop-cap` 五种子复跑并审计，1秒率为53.30/52.59/52.28%，5秒率为54.09/53.72/53.90%，控制airtime累计均值252.6/289.4/304.2秒；15份事件流与旧对照对应快照一致。三档统一6秒待发现缓存，不能以5秒率代替1秒率，也不能外推真实RF。

按有方向节点对统计，旧交叉 seed0 的870对均有业务、7对未在1秒内收到；重组 seed0 为99对。只代表单次模拟和对应时限，不证明持续不可达。`failure_followup.json` 的链路失败至同流下次送达时间包含等待新业务，不等于路由恢复时间。

## 资源与待解决事项

修复前 `29-long-adaptive` 三个6小时仿真均通过端点和采样审计，但 seen 128项、peer20项达到采样上限；每分钟采样可能漏瞬时峰值。最新 `48-latest-long` 三种子各6小时仿真均完成并通过端点与每分钟资源审计，1秒率54.66/54.74/54.96%，seen均达到128项上限且每组累计溢出约33万次；这不是实板耐久。

`bitmap/` 将重复请求按来源和boot压入64位窗口；高负载旧版同源比较中表满降为0，但控制airtime +35.7%、1秒率 -2.20个百分点；进一步限制中继转发也未解决，不建议直接采用。窗外合法乱序、boot身份认证、重放风险仍存在。`source_cap/` 单独试源端限速，旧版压力下减控制约6.4%但率略降，仍不足解决拥塞。

`41-deferred-target`：ESP32-S3最小工程静态链接核心相对空壳固件+5376 B、BSS+28416 B；不含ESP-NOW集成、实时堆栈或烧录。`epoch/` 是独立实验v3：在持久递增源boot假设下可更换源的反向路径，主机四节点特定源重启换路径夹具通过，最新加锁版 `57-locked-source-reboot` 五种子模拟中重启源交付未见改善；目的重启、旧DATA/RERR、认证、防重放、真实持久化均未解决，不能称为完整重启方案。`restart_diagnostic.c` 证明v2在源boot改变且序号重置时可能沿用旧逆向路由。
