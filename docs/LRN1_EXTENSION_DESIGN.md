# LRN1 扩展设计：给网关发什么（面向前端展示）

状态：**设计稿，未实现**。目标是把"节点/边缘能提供什么"与"前端能展示什么"对齐。

原则：
- **GPS 位置位必须预留**（现在没硬件，字段先占位、填 0，前端显示"无定位"）。
- 其余字段按**前端能不能用上**取舍：用不上的不加，省空口。
- 保持一帧自包含：网关收到一帧就知道这个节点的完整状态。

---

## 1. 为什么不是简单加几个字节

现在的 LRN1 是「帧头 44 + 邻居行 20×n + CRC 4」，最多 8 行 = 208 字节。
直接往后追加会和"最多 8 个邻居"冲突（8 行已经占满 208）。

因此采用**可选块 + 头部标志位**：

```
字节 6 的 flags:
  bit0 邻居表已满
  bit2 tx_delay 已填写
  bit3 状态块存在      ← 新增
  bit4 GPS 块存在      ← 新增
```

解码端按标志位算长度，不必改魔数：

```
len = 44 + 20*rows + (24 if status) + (20 if gps) + 4
```

**容量随之调整**：带状态块 + GPS 块时，邻居行上限从 8 降到 **5**（44+100+24+20+4 = 192 B，仍小于 208）。
邻居少时（常见 3-4 个）不损失任何行。

## 2. 状态块（24 字节）

| 偏移 | 长 | 字段 | 类型 | 前端用途 |
|---:|---:|---|---|---|
| 0 | 1 | `reset_reason` | u8 | 节点卡片标"重启原因"：上电/欠压/看门狗/软复位 |
| 1 | 2 | `supply_mv` | u16 | **电压表**；低于阈值变红（欠压预警） |
| 3 | 1 | `die_temp_c` | i8 | 温度显示 + 过热着色 |
| 4 | 1 | `heap_free_kb` | u8 | 内存水位条，长期下降=泄漏 |
| 5 | 1 | `queue_depth` | u8 | 发送队列积压 |
| 6 | 1 | `tx_drops` | u8 | 丢帧计数 |
| 7 | 1 | `routes` | u8 | 当前路由条数（多跳健康度） |
| 8 | 1 | `lora_tx_power_dbm` | i8 | 详情面板：实际发射功率 |
| 9 | 1 | `lora_sf` | u8 | 详情面板：当前扩频因子 |
| 10 | 1 | `fault_flags` | u8 | bit0 曾欠压 · bit1 曾看门狗 · bit2 表满 · bit3 曾热保护 |
| 11 | 1 | `pi_flags` | u8 | bit0 边缘在运行 · bit1 有网络 · bit2 有 GPS 源 |
| 12 | 1 | `pi_cpu_temp_c` | i8 | **边缘核心温度**（Pi 过热是真实风险） |
| 13 | 1 | `pi_load_x10` | u8 | CPU 占用（0-25.5） |
| 14 | 2 | `pi_mem_free_mb` | u16 | 边缘内存 |
| 16 | 1 | `pi_wifi_rssi` | i8 | 链路上有网时的信号 |
| 17 | 1 | `serial_errors` | u8 | Pi↔节点 串口错误（链路稳定性） |
| 18 | 1 | `battery_pct` | u8 | 0=未知；有电池时显示电量 |
| 19 | 5 | `reserved` | — | **留给后续**（任务ID、告警、传感器） |

> `pi_*` 字段由 Pi 通过串口周期喂给节点（新增一条 `edgestat` 命令），节点存住，
> 下次组帧时带上。Pi 掉线时 `pi_flags.bit0=0`，前端立刻能看出"边缘没了但节点还在"。

## 2.5 实现状态（重要：格式有位置 ≠ 现在有数据）

帧**格式**已经支持下面全部字段，但当前固件只填了两个。看数据时必须分清：

| 字段 | 现在有值 | 缺什么 |
|---|---|---|
| 
eset_reason | **✅ 真实值** | — |
| heap_free_kb | **✅ 真实值** | — |
| supply_mv | ❌ 恒为 0 | 需要 lr11xx_system_get_vbat()，并解决从工作线程访问射频上下文 |
| die_temp_c | ❌ 恒为 0 | 需要启用 	emperature_sensor 驱动 |
| queue_depth / 	x_drops | ❌ 恒为 0 | 需要从 runtime/peer_manager 暴露计数 |
| 
outes | ❌ 恒为 0 | 需要读 source_route 表长度 |
| lora_tx_power_dbm / lora_sf | ❌ 恒为 0 | 从 lref_config 读取即可，改动很小 |
| ault_flags | ❌ 恒为 0 | 需要累计型故障计数器 |
| pi_*（7 个字段） | ❌ 恒为 0 | 需要新增 Pi→节点 串口命令（如 edgestat）+ Pi 侧发送服务 |
| attery_pct | ❌ 恒为 0 | 需要电池采样电路 |
| GPS 块全部字段 | ❌ 恒为 0 | 需要定位源（飞控或 GNSS 模块） |

发送节奏：状态块**每 5 帧带一次**，10 s 周期下即 **50 s 一个采样点**。
需要更高分辨率时可以改 LRN1_STATUS_EVERY，代价是邻居行变少。

## 4. 前端能因此多显示什么

| 前端区域 | 现在 | 加上之后 |
|---|---|---|
| 节点卡片 | 编号、年龄、邻居数 | **电压、温度、内存、重启原因** |
| 状态药丸 | 在线/失效 | + **欠压 / 过热 / 边缘离线** 三种新告警 |
| 详情面板 | LoRa RSSI/SNR | + **SF、发射功率、队列、丢帧、路由数** |
| 地图 | 手动布局 | **GPS 布局真正可用**：真实落点、航向箭头、速度 |
| 边缘面板 | 无 | **Pi 的 CPU/内存/温度/串口错误** |

## 5. 空口代价

| 组合 | 帧长 | 空中时间（SF7/BW125） | 占空比（10 s 周期） |
|---|---:|---:|---:|
| 现在（3 邻居） | 108 B | ~180 ms | 1.8% |
| 仅状态块（3 邻居） | 132 B | ~215 ms | 2.2% |
| 状态 + GPS（3 邻居） | 152 B | ~245 ms | 2.5% |
| 状态 + GPS（5 邻居，上限） | 192 B | ~305 ms | 3.1% |

**最坏情况仍低于现在的 8 行满帧（208 B / 330 ms）**，所以不会比现状更差。
