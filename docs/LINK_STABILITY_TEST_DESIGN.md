# 链路稳定性实验设计（5 节点实机 · LoRa 上行 + ESP-NOW 组网）

对象：5 × 树莓派（eora-air-01..05）+ 5 × EoRa 节点 + 1 × 亿佰特 E870-L 网关。
目标：判定这条链路**能不能长时间稳定工作**，并在出问题时**指得出是哪一层坏的**。
指标口径与 `docs/EXPERIMENT_PLAN.md` 保持一致，便于与仿真结果对照。

---

## 0. 先决条件（不做完，实验没有意义）

| 项 | 为什么必须先做 |
|---|---|
| **刷入带状态块的固件**（`BUILD-20261118-lrn1-status`） | 否则**分不清"重启"和"丢包"**。`observer_boot` 变化只能说明重启过，说明不了原因；状态块给出 `reset_reason`（上电/欠压/看门狗/panic）和 `heap_free_kb`，这才是稳定性的直接证据 |

| 五台 Pi 时间同步（NTP 或 `timedatectl`） | 否则跨节点时间无法对齐，只能退化成"间隔统计" |
| 记录基线配置 | 帧周期、SF、发射功率、网关信道，写进 RUN_MANIFEST |

> 当前状态：**状态块固件还没刷进实机**（上次三台离线）。所以第一步是 `FLASH_NODES.cmd`，不是直接开测。

## 1. 观测点（三处，互不依赖）

| 层 | 来源 | 能回答什么 |
|---|---|---|
| **空中** | `topology_server` 的 `/api/v1/lora/topology` | 网关到底收到了什么：帧、序号、boot、RSSI/SNR、邻居状态 |
| **节点内部** | 每台 Pi 的 `~/eora/logs/node_events.jsonl` | 串口链路、路由、队列、ESP-NOW 收发计数 |
| **主机** | 每台 Pi 的 `vcgencmd` / `/proc` | CPU 温度、负载、内存、串口错误 |

三层同时记，出问题才能判断"是 LoRa 丢了、还是节点没发、还是 Pi 挂了"。

---

## 2. 指标定义

设单节点上报周期 `P = 10 s`，观测时长 `T`。

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **RDR（上报到达率）** | `实收不同帧数 / floor(T/P)` | 按 `(observer_boot, report_seq)` 去重 |
| **AoI P50/P95/max** | 采样时刻"最新一帧的年龄" | `pc_receive_age_ms` 时间序列 |
| **帧间隔 P95/最大值** | 相邻两帧到达时间差 | 由 `seq` 变化时刻推算 |
| **中断次数** | 间隔 > 2P 的次数 | 同上 |
| **重启次数** | `observer_boot` 变化次数 | 每节点独立计数 |
| **重启原因分布** | `reset_reason` 直方图 | 状态块 |
| **解析失败** | `bad_frames`、`foreign` | 接收服务计数 |
| **LoRa 链路漂移** | 首 30 min 与末 30 min 的 RSSI/SNR 均值差 | 状态块外的网关侧元数据 |
| **网格完整度** | 实际双向邻居对数 / 期望对数 | `neighbors.state == bidirectional` |
| **截断率** | `rows / total_rows` < 1 的帧占比 | 帧头 |
| **堆水位** | `heap_free_kb` 的最小值 | 状态块 |
| **恢复时间** | 节点失联后重新出现所需时间 | 由 AoI 序列推断 |

## 3. 判据（**跑之前定死，不许事后调整**）

| # | 判据 | 门槛 |
|---|---|---|
| C1 | 每节点 RDR（连续 2 h） | **≥ 99.0 %** |
| C2 | 未解释重启 | **0 次**（`reset_reason` 为 BROWNOUT/WATCHDOG/PANIC 一律算失败，需给出解释） |
| C3 | AoI P95 | **≤ 15 s**（1.5 × 周期） |
| C4 | `bad_frames` | **0** |
| C5 | 五台同房间时的网格完整度 | **= 100 %**（10 对全双向） |
| C6 | 网关静默检测时间 | **≤ 60 s** |
| C7 | 网关恢复时间 | **≤ 120 s** |
| C8 | `heap_free_kb` 24 h 内 | 不下降低于基线的 70 % |

判定规则：**C1–C5 任一不过 → 稳定性不成立**；C6–C7 是运维可用性，单独报。

## 4. 实验序列（单因子，一次只动一个变量）

| 编号 | 场景 | 时长 | 目的 |
|---|---|---|---|
| **T0** | 基线：五台同处一室、静止、无业务 | 2 h | 建立正常分布（AoI、RSSI、帧间隔） |
| **T1** | 距离扫描：一台逐步挪远（每档 ~10 m 或按 RSSI −5 dB 一档），每档停 10 min | ~1 h | 找出 LoRa 上行与 ESP-NOW 各自的**实际边界**，画出 RSSI→RDR 曲线 |
| **T2** | 供电扰动：逐台拔插 USB / 断电 3 s | 15 min | 验证 `reset_reason=BROWNOUT` 能被记录，测重入网时间 |
| **T3** | 网关转发器静默：等待自然发生，或强制重启转发器 | 观测 | 测 C6/C7，验证前端能如实显示 `stale` |
| **T4** | 24 h 长稳 | 24 h | 抓缓慢退化（堆泄漏、温漂、时钟漂移） |
| **T5** | 同时重启五台 | 15 min | 重入网风暴：五台同时 hello/入网是否拥塞 |
| **T6** | 2.4 GHz 干扰：同频大流量（另一台设备刷流量） | 30 min | 只打 ESP-NOW，确认它先于 LoRa 掉 |
| **T7** | Pi 满载：`stress-ng` 打满 CPU | 30 min | 看 `node_reader` 是否丢帧、串口是否溢出 |

**顺序理由**：T0 先建立正常值，否则后面所有"异常"都没有参照。

## 5. 数据归档

```
simulation/outputs/<任务ID>/<run-id>/
  RUN_MANIFEST.json        按 coordination/templates/RUN_MANIFEST.json
  raw/topology.jsonl       每 2 s 采样一次
  raw/pi_<host>.jsonl      每 10 s 一次主机指标

  analysis/summary.csv     每场景一行
  analysis/REPORT.md       结论 + 图
```

每个场景**至少重复 3 次**，报中位数与离散度，不只报最好的一次。

## 6. 当前系统的盲点（会限制结论强度，必须写进报告）

1. **没有节点间时钟同步** → 无法测真正的单向时延，只能用 AoI 与帧间隔作为代理。
2. **LoRa 上行没有重传/ACK** → 丢帧只能从 `seq` 缺口推断，无法区分"没发"与"发丢"。
   （状态块里的 `tx_drops` 能补一部分。）
3. **网关只有一个**，无法区分"节点发丢"与"网关漏收"；多接收端才能分离这两个因素。
4. 样本量小（5 台），统计功效有限；结论应限定为"这 5 台在此环境下"。
